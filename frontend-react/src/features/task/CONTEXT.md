# Task Feature

## Overview

Core task management: card-grouped grid/table hybrid at `/`, filtered/paginated list, detail drawer, subtasks, tags.

## Pages

- `TaskCardPage` (`/`, formerly `TodayPage` — the old date-computed "Hôm nay"/"Quá hạn" concept is gone, see Business Rules #1) — grid of `task-card`'s cards (`TaskCardGrid`) when none is selected; clicking one swaps the whole page to a `TaskListPage`-style table (`TaskFilters` + `TaskTable` + pagination) filtered by `cardId`, all in local `selectedCardId` state (not a route param — same "no separate route per selection" convention as `random-draw`'s `RandomDrawPage`). "Thêm việc" (both the grid header's global one and the in-card one) opens `AddTaskToCardDrawer` — a picker requiring a destination card, defaulting to whichever card is currently open.
- `TaskListPage` (`/tasks`, `/lists/:id`) — table (`TaskTable`), filters + sort + page/`limit` (10/20/50/100) synced to URL, row checkboxes + bulk delete bar.
- `TaskDetailPage` (`/tasks/:id`) — thin wrapper that opens `TaskDetailDrawer`; `onClose` calls `navigate(-1)`

## Components

- `TaskItem`, `TaskList`, `SortableTaskItem` — the old card/drag-to-reorder rendering. **No page imports these anymore** (both `TaskCardPage` and `TaskListPage` use `TaskTable`) — kept only because `useReorderTasks`/`PATCH /tasks/reorder` still exist backend-side; dead code otherwise, candidate for removal if that endpoint is ever dropped too.
- `TaskTable` — shared by both pages. Columns: checkbox, Tiêu đề, Danh sách, Trạng thái, Ưu tiên, Điểm (`task.points`, `—` if unset — pre-existing tasks predate the field), Hạn chót, Hành động (bắt đầu làm → `onStart(task)`, see `useStartTask`, disabled for `done`/`cancelled`; chỉnh sửa → `TaskFormModal` edit mode; xoá → `onDelete(task)`, caller decides what that means). `isOverdue` prop adds the red left border (on the first `<td>`, not the `<tr>` — border on a table row doesn't render under the default `border-collapse: separate`) — unused since `TaskCardPage` dropped the overdue-highlighting Today view, kept for any future caller. `deleteLabel`/`deleteIcon`/`deleteIsDangerous` let a caller re-skin the delete action's meaning; don't add a caller with yet another meaning without adding a matching set of props — the point is that the icon/label always tells the truth about what `onDelete` actually does.
- `AddTaskToCardDrawer` (formerly `AddTodayTaskDrawer`) — search/status/priority/list filters over `useTasks`, plus a **required** "Thẻ đích" select up top; per-row "Thêm vào thẻ" button sets `cardId` (`PATCH /tasks/:id`), "Tạo mới" escape hatch into `TaskFormModal` pre-filled with the chosen card. `defaultCardId` prop seeds the destination select — since the drawer component itself never unmounts (only `Drawer`'s rendered content conditionally does, see `shared/components/ui/Drawer.tsx`), a plain `useState(defaultCardId...)` initializer only runs once; re-syncing it on every fresh open uses the same render-time "adjust state when a prop changes" pattern as `auth/pages/ProfilePage.tsx`, not an effect (cost real debugging time — first version silently created every new task with `cardId: null` on the 2nd+ open of the drawer).
- `TaskFilters` — search (debounced 400ms) + status/priority toggle chips + tag select + sort select (packs `sort:order` into one `<select>` value — "Mới nhất"/"Cũ nhất" over `createdAt`, "Khối lượng: cao→thấp/thấp→cao" over `points`), all synced to `useSearchParams`. Shared by `TaskListPage` and `TaskCardPage`'s in-card table.
- `TaskFormModal` — create/edit (title, description, list, **thẻ (card)**, priority, due date, estimate, **điểm/point**, tags); no `parentTaskId`/`recurrenceRule` field here — subtasks are created from `SubtaskList`'s quick-add instead. `points` is **required** on every save (create or edit) — `CreateTaskPayload.points: number` is non-optional; `SubtaskList`'s quick-add bypasses this form entirely and just sends `points: 0`. `defaultListId`/`defaultCardId` prefill their selects; `defaultDueDate` prefills "Hạn chót" (used by `AddTaskToCardDrawer`'s "Tạo mới"). Uses react-hook-form's `values` (not `defaultValues`) specifically so these defaults re-apply whenever the modal's props change between opens — no manual re-sync needed here, unlike `AddTaskToCardDrawer` above.
- `TaskDetailDrawer` — inline-editable title/description (click, blur to save), status/priority selects (invalid transitions greyed out via `TASK_STATUS_TRANSITIONS`), due date, list, tags (`TagPicker`), subtasks, delete (archive) with `ConfirmDialog`
- `SubtaskList` — checklist + quick-add input (creates a task with `parentTaskId`)
- `TagPicker` — chips + existing-tag select + inline "new tag" input
- `StatusBadge`, `PriorityBadge` — data-driven colors from `index.css` `@theme` tokens (UI-SPEC.md)
- `TaskTimerClock` — pure countdown-UI (title, minutes, optional `hostWindow`), shared by `TaskTimerFloatingPanel` (in-page, same window) and `TaskTimerPipHost` (Document PiP, a different `hostWindow`) so the two only ever differ in *where* this renders. Takes `hostWindow` because a PiP window is a second, separate `Window`/`document` — `setInterval`/`document.title`/`AudioContext` must all target *that* window, not the opener's, or the countdown/title/beep silently happen in the wrong place.
- `TaskTimerPipHost` — mounted once at the app root, renders only when the active session has a `pipWindow` (see Business Rules #8). Portals `TaskTimerClock` into it via `createPortal`, copies the opener's stylesheets + `<html>` class (dark mode) in — a PiP window starts as a bare `about:blank` document with none of that.
- `TaskTimerFloatingPanel` — mounted once at the app root too, renders only when the active session has **no** `pipWindow` (the fallback path). A plain `position: fixed` card, dragged via pointer events clamped to the viewport. Both host components read the same `useTaskTimerStore` session; exactly one of them ever renders anything for a given session.

## Hooks

- `useTasks(params, options?)`, `useTask(id)` — queries. `options.enabled` exists specifically so `TaskCardPage` can skip fetching `GET /tasks` entirely while on the card grid (no card selected yet) instead of firing an unfiltered "every task" request that's immediately thrown away.
- `useCreateTask()`, `useUpdateTask()`, `useDeleteTask()`, `useBulkDeleteTasks()` — mutations, invalidate `['tasks']` + `['stats']` + **`['task-cards']`** (any of these can move a task on/off a card, which moves that card's `taskCount` in the grid — easy to forget since `task-cards` reads like an unrelated feature's cache key). Bulk hits `DELETE /tasks/bulk` (body `{ ids }`), one transaction backend-side. **Only `TaskListPage`/`TaskCardPage` call the delete hooks** — they archive (`is_archived = true`).
- `useUpdateTaskStatus()` — **optimistic**: patches the task in every cached shape under the `['tasks', ...]` prefix (detail object, paginated list, today view) before the request resolves; rolls back all of them on error
- `useStartTask()` — "Bắt đầu làm": requires `task.estimateMinutes` set (toasts and bails otherwise — no default duration); prefers Document Picture-in-Picture (`window.documentPictureInPicture.requestWindow()`, Chrome/Edge 116+ — see Business Rules #8), falls back to the in-page session on other browsers. Either way, for a `todo` task it also fires `useUpdateTaskStatus` to `in_progress` (skipped if already `in_progress`, so re-opening the timer doesn't re-fire it). **`requestWindow()` runs before the status mutation, not after** — it's only granted synchronously off a user gesture; awaiting the (async) status mutation first breaks that and the request gets silently refused.
- `useTaskTimerStore()` (Zustand, `stores/taskTimer.store.ts`) — holds the single active timer `session` (`{ taskId, title, minutes, pipWindow? }` or `null`). `pipWindow` present ⇒ `TaskTimerPipHost` renders it; absent ⇒ `TaskTimerFloatingPanel` does. Opening a new session while one is active replaces it (closing any existing `pipWindow` first) — one timer at a time.
- `useReorderTasks()` — optimistic reorder of the currently-open list query
- `useReplaceTags()`, `useTags()`, `useCreateTag()` — tag management

## Business Rules

1. **`/` is no longer a date-computed "Today" view (2026-08-31).** `TaskCardPage` groups tasks by `task-card`'s manual `cardId`, which carries **no date/calendar meaning** — a card named "Hôm nay" is just a card someone typed that name into, same as one named "Lễ 2/9". `GET /tasks/today|overdue|upcoming` and `useTodayTasks`/`AddTodayTaskDrawer` still exist backend-side (dead, unused) but were removed frontend-side; don't resurrect the old "trust the server's date split" assumption for this page.
2. Status dropdown disables options that aren't a valid transition from the current status (mirrors backend `TASK_STATUS_TRANSITIONS`) — but the server is still the source of truth; a stale client can still get `TASK_003` back, shown via `getErrorMessage`
3. Toggling the checkbox on a task with unfinished subtasks can fail with `TASK_005` — optimistic update rolls back and shows the mapped Vietnamese message
4. Invalidate `['tasks']` (prefix) + `['stats']` + `['activities']` after any status change — `['stats']`/`['activities']` are inert right now since those features aren't built yet, kept for when they are
5. Drag-to-reorder is no longer exposed in the UI on either page (both are `TaskTable` now) — `useReorderTasks`/`PATCH /tasks/reorder` are unused but left in place
6. Never build a `dueDate` from Luxon's `.endOf('day')` (23:59:59.999) — `due_date` is a `DATETIME` with no fractional-second precision, so MySQL rounds `.999` up to `00:00:00` the *next* day. Use whole-second precision instead (`.set({ hour: 23, minute: 59, second: 59, millisecond: 0 })`) if a "due by end of today" moment is ever built again.
7. **Removing a task from a card is `PATCH { cardId: null }`, never an archive.** Same "explicit `null` = clear, `undefined` = leave alone" contract `dueDate` already used — `UpdateTaskPayload.cardId` inherits it for free via `Partial<Omit<CreateTaskPayload, ...>>` since `CreateTaskPayload.cardId` was already `number | null`. Deleting a whole card (`task-card`'s `DELETE /task-cards/:id`) does this same clearing server-side for every task on it, in bulk.
8. **The "Bắt đầu làm" timer prefers Document Picture-in-Picture over an in-page panel, on purpose, despite its ugly origin bar.** History: first built as `window.open` (full address bar). A user wanted that gone → tried Document PiP (smaller, but still a mandatory "localhost:5173" bar — no window feature/API suppresses it on *any* real separate window, by design, for anti-phishing; see [WICG's Document PiP spec](https://wicg.github.io/document-picture-in-picture/)) → switched to a pure in-page floating panel instead, which has zero browser chrome since it isn't a real window at all → then the user pointed out the actual requirement: the timer must stay visible even after switching browser tabs, which **only** a real always-on-top window (PiP) can do — an in-page panel is part of one tab's DOM and simply isn't rendered while another tab is focused. Net result: PiP is preferred (ugly bar, but persists across tabs); the in-page panel is only the fallback for browsers without the API. Don't "clean up" this back to panel-only without re-confirming the cross-tab requirement no longer matters.

9. `points` ("khối lượng", 1 point ≈ 1 ngày by the user's own convention — nothing computed from it) is required in `TaskFormModal` for both create and edit, but the DB column is nullable — pre-existing tasks show `—` in `TaskTable` until someone edits them and fills it in. `RandomDrawService`-style "clamp instead of reject" doesn't apply here; this one really is a hard required field at the form/DTO level.

## Not implemented in this pass

- Comments, attachments, activity/history tab in the detail drawer — depend on `collaboration`/`activity` features, not built on either side yet
- Reassigning a task to another user from the drawer — needs a user picker, which needs `user-management`; the `PATCH /tasks/:id/assignee` service call isn't wired to any UI yet
- `recurrenceRule` — no form field; the backend accepts and validates it, but nothing in the FE sets it
- Statistics/History quick links in the sidebar (see `task-list/CONTEXT.md`)

## Dependencies

- auth (current user's timezone shown implicitly via server responses; permission-driven UI is minimal since the server enforces ownership)
- task-list (list picker in `TaskFormModal`/`TaskDetailDrawer`, list name shown on `TaskItem`)
- task-card (`useTaskCards`/`TaskCardGrid` for `TaskCardPage`'s grid; card picker in `TaskFormModal`/`AddTaskToCardDrawer`)
